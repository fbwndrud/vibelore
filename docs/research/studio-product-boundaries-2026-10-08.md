# 제작 Studio의 제품 경계와 다인물 편집 설계

2026-10-08. 현재 저장소 계약과 이전 매체 설계에 대한 제품 설계 검토다. 구현이나 유료 모델 실험의 완료 기록이 아니다. 이번 문서가 제안하는 독립 Studio, 신규 제작 원천, 오디오 배역과 편집 기능은 현재 구현되지 않았다.

## 권고: 하나의 제작 엔진, 별도로 사용할 수 있는 Studio

**Studio는 vibelore 없이도 프로젝트를 열고 원천·대본·그림·음성을 반입하거나 생산하고 최종 제작물을 내보내는 제품으로 만든다. vibelore는 가장 깊이 연결된 원천 제공자다.** 독립 제품이라는 말은 지금 별도 저장소·계정·클라우드 서비스를 반드시 만들라는 뜻이 아니다. 첫 구현은 같은 모노레포의 별도 앱과 패키지로 시작할 수 있다. 중요한 조건은 Studio가 vibelore의 소설 workflow와 저장 포맷에 종속되지 않는 것이다.

```text
vibelore                 파일/대본/에셋 반입                 Studio 원창작
정본·세계·원작             이미 존재하는 창작 자료              제작용 이야기·대본
   │                             │                              │
   └─────────────── Source Connector / Import ──────────────────┘
                                 │
                   보존된 원천 + 제작 프로젝트
                                 │
                공유하는 Headless Production Engine
                  각색·배역·에셋·작업·검사·출력
                        │                   │
                    Studio UI          자동화/MCP API
                        └────── Worker ──────┘
                      이미지·음성·미리보기·렌더
```

MCP는 Studio 화면의 원격 제어기이자 headless 제작 입구다. Studio를 열기 위해 채팅 호스트가 항상 살아 있어야 한다거나 사용자가 매번 request ID를 전달해야 하는 제품으로 만들지 않는다. 장시간 작업의 상태와 재개는 엔진이 소유한다. UI·MCP·worker가 각자 workflow 승인을 다시 구현하면 서로 다른 ‘완료’ 판정이 생긴다.

| 선택지 | 장점 | 큰 비용 | 판단 |
|---|---|---|---|
| vibelore MCP 내부의 확장 기능 | 현재 정본·검사 재사용이 빠름 | 모든 화면·자산·긴 작업이 소설 저장소와 호스트 수명에 묶임 | 소규모 headless 실험까지 |
| 완전히 별도 SaaS | 팀 작업·계정·배포가 선명함 | 인증·결제·업로드·보안·동기화가 연출 품질 검증보다 먼저 들어옴 | 검증 후 운영 선택지 |
| 독립 Studio 앱 + 공통 제작 엔진 + vibelore Connector | UI 제품으로 성장하면서 기존 정본 원칙을 보존 | 명시적인 원천 계약과 경계를 먼저 설계해야 함 | 권고 |

## 현재 구조에서 반드시 살릴 것과 벗어날 것

현재 `ProductionSource`는 소설 화 또는 채택한 독립 장면 대본을 받는다. 대본 경로는 정확한 원문·장면별 인물 상태·표현·승인 에셋 바이트를 봉인하며 소설 Foundation을 만들지 않는다. 이는 ‘소설만 가능’이라는 제약이 이미 전부인 것은 아니라는 근거다. 반면 계약이 `workId`, vibelore store와 `.vibelore` lock을 직접 읽으므로 독립 Studio 원천 계약으로 그대로 내보낼 수는 없다. [현재 resolver](../../src/core/production-source.js), [공유 런타임](../reference/SHARED_LORE_RUNTIME.md).

Connector는 vibelore resolver를 호출하고 그 결과를 versioned `SourceBundle`로 내보낸다. Studio가 `.vibelore/` 내부 파일을 직접 편집·소유하지 않는다. novel 원천은 기존 sourceVersion 1의 보존 제약을 정확히 표시하고, 새 완전 보존 bundle은 새 계약으로 구별한다. 과거 결과를 보존되었다고 소급 표시하지 않는다.

현재 용어에서 세계·작품·세계선·정본 판본·인물 상태·표현·제작물을 분리한다. Studio는 이 구분을 유지하되 일반 파일 반입 사용자에게 공유 세계 등록부를 강제로 만들게 하지 않는다. [CONTEXT.md](../../CONTEXT.md), [독립 HEAD와 binding 계약](../reference/SHARED_LORE_RUNTIME.md).

## 세 가지 시작 방식: 생산도 이 안에서 할 수 있다

1. **원작에서 제작:** vibelore 또는 원고 파일을 연결하고 범위·당시 상태·원작 대응표를 고정한다. 원작 보존 검사와 각색 선택이 적용된다.
2. **제작용 이야기를 새로 만들기:** Studio에서 이야기 브리프·장면 대본·배역을 작성하거나 생성한다. 생성 초안과 채택 대본을 구별한다. 소설 정본이 존재한다고 가장하지 않으며 독립 `original-script` 원천을 사용한다. 제작 전 최소 사건 순서·인물 의도·공개 계획을 갖는다.
3. **혼합 제작:** 반입 대본과 기존 그림·음원에서 시작하고 빈 배역·샷·환경음만 새로 만든다. 외부 자료가 어느 대사·샷에 대응하는지 명시적으로 연결한다. 모델 추정으로 캐릭터 이름이나 파일명만 맞춰 승인하지 않는다.

빈 프로젝트도 대본→공연→타임라인 경로를 따른다. ‘자료가 없으니 생성’은 이야기 없이 무작위 그림·목소리를 나열하는 버튼이 아니다. 빠른 러프 생성은 미확정 항목을 드러내는 animatic을 만든다. 기존 고품질 자료를 다시 생성하는 일을 기본으로 삼지 않는다.

Studio 원창작의 공유 세계 역수출이 필요하면 ‘설정 후보 보내기’를 별도 제공한다. vibelore가 이를 자신의 정본 검토·채택 workflow로 처리한다. Studio 승인과 vibelore 정본 채택을 하나의 분산 transaction이나 버튼으로 합치지 않는다.

## 소유권과 판본: 승인 동사가 다섯 가지다

| 판단 | 변경하는 것 | 바꾸지 않는 것 |
|---|---|---|
| 원천 업데이트 채택 | 프로젝트의 새로운 source binding | 과거 제작판·세계 정본 |
| 대본 채택 | 제작 프로젝트의 각색/대본 판본 | 원작의 사건과 문구 |
| take/샷 사용 | 특정 장면 또는 출력판의 선택 | 공통 인물 기준 에셋 |
| 표현 기준 채택 | 프로젝트 또는 공유 라이브러리의 기준 그림·배역 판본 | 기존 장면의 고정 참조 |
| 공유 정본 채택 | 원천 시스템이 소유한 사실과 원문 | 다른 작품의 binding과 제작 출력 |

화면에는 문맥에 맞는 이름을 쓴다. ‘이 샷에 사용’, ‘이 작품의 기준으로 채택’, ‘공유 라이브러리에 등록’, ‘원작 변경 후보 보내기’가 서로 다른 행동이다. 모두 같은 ‘승인’ 버튼이면 잘못된 전파를 막기 어렵다.

프로젝트는 선택한 원천·대본·배역·에셋·타임라인·출력판의 독립 HEAD를 가진다. 라이브러리의 새 기준은 ‘새 판본 이용 가능’으로 보여주고 기존 제작판을 자동 갱신하지 않는다. 새 버전 선택 시 영향 목록을 확인하고, 실행 직전 참조 판본이 여전히 같아야 한다. 다른 작업자가 그동안 고쳤으면 기존 후보가 현재 HEAD를 덮지 못한다.

## 다인물 모델: 인물, 배역, 등장, 발화, 화면은 서로 다르다

첫 샘플의 A/B는 데이터 구조가 될 수 없다. 엔진의 cast는 임의 길이의 안정적인 ID 집합이다. provider가 두 화자만 허용하는 것은 생성 요청 한 건의 제한이며 작품 배역 수의 제한이 아니다.

| 자료 | 의미 | 예 |
|---|---|---|
| `Entity` | 이야기 인물의 정체성 | 동일 인물의 어린 시절과 성인 |
| `Role` | 이 작품에서 수행하는 역할 | 본인 발화·내면 음성·내레이터·비인격 안내방송 |
| `VoiceBinding` | 언어·상태·표현별 채택 음색 | 어린 시절 한국어 배역, 성인 한국어 배역 |
| `SceneOccurrence` | 장면에서의 등장과 상태 | 현장·전화 너머·회상·군중 구성원 |
| `Utterance` | 실제 발화/목소리 사건 | 화자·수신자 여러 명·응수 대상·발화 의도 |
| `ShotAppearance` | 어느 프레임에서 어떤 모습이 보이는지 | 말하는 사람은 화면 밖, 듣는 세 명은 화면 안 |

같은 목소리 actor가 여러 role을 맡을 수 있고, 같은 Entity에 상태·언어별 여러 VoiceBinding이 있을 수 있다. 화면에 보이는 인물과 말하는 인물이 항상 같다는 가정을 제거한다. 전화·방송·군중·내면 음성·동시 발화는 특별한 A/B 예외 분기 대신 역할과 occurrence로 표현한다. 화자와 수신자는 다른 필드다. 침묵 중인 수신자도 reaction cue의 주체가 된다.

익명 군중은 `group-role`을 제공할 수 있지만 중요한 군중 발화는 별도 utterance와 voice binding으로 관리한다. 익명성이 이야기의 반전이라면 화면 표시 이름과 내부 정체성은 별도로 보존한다. 화자의 진짜 이름을 자막에 자동 넣어 스포일러를 만들지 않는다.

## 2명·8명·40명을 같은 화면에서 다루기

‘작품 전체 배역 40명’과 ‘동시에 말하는 40명’을 구별한다. 엔진은 동시 audio event를 표현할 수 있지만 공급자별 처리 한도·연출 가독성·mix 검증은 따로 적용한다. 40명의 줄을 상시 펼치는 UI는 쓰기 어렵다.

| 규모 | 기본 화면 | 필요할 때 확장 |
|---|---|---|
| 2명 | 발화·샷·표정·자막이 연결된 간단 timeline | 배역 take와 의도 비교 |
| 8명 | 현재 장면의 등장/발화 순서, 선택 인물 트랙 확장 | 동시에 말하는 구간의 충돌 표시, 같은 장면의 offscreen 목록 |
| 작품 전체 40명 | 검색 가능한 Casting Library, 현재 장면의 3~8명만 표시 | 상태·언어·등장 화·배역 준비 여부로 필터, 미해결 배역 사용처 목록 |

트랙 접기·화면 필터는 render에서 mute/hide하는 동작과 분리한다. 이름 변경이 연결을 끊지 않도록 참조는 ID를 쓴다. 큰 프로젝트는 scene 단위로 로드하고 긴 timeline과 배역 목록을 가상화한다. 모든 waveform과 고해상도 그림을 프로젝트 진입 때 동시에 decode하지 않는다.

배역 준비 표는 ‘목소리 있음’, ‘실제 샘플 청취’, ‘이 상태에 사용 가능’, ‘사용 중인 take 수’를 구별한다. 단순 초록 완료 상태로 전체 역할을 합치지 않는다. 내레이터는 별도 role이며 작품 차원 사용 정책과 장면 차원 발화 override를 갖는다.

## 화면은 하나의 작업대, 선택 대상에 따라 도구가 바뀐다

주요 탐색은 **프로젝트 → 장면 → 선택 대상**이다. 프로젝트 홈에서 원천·대본·배역·에셋·출력의 준비와 막힌 작업을 본다. 장면 작업대에서는 대본/원작, 실제 프리뷰, 선택 inspector, timeline을 연결한다. 별도 이미지·음성 제품으로 계속 이동하지 않는다.

- 발화를 선택하면 표시 문구·발음·의도·상대·take A/B·trim·실제 파형이 나온다.
- 샷을 선택하면 구성 레이어·초점·카메라·이미지 수정·세로/가로 구도·자막 안전 영역이 나온다.
- 인물을 선택하면 작품 전체와 현재 장면의 상태·목소리·외형·사용처가 나온다.
- 비어 있는 필요한 자료를 선택하면 생성 또는 파일 반입이 나온다. 사용 가능한 자료가 있으면 재사용 후보부터 보여준다.

현재 화면의 선택과 생성 job은 따로 관리한다. 생성이 끝났다고 사용자가 보고 있던 장면을 바꾸거나 자동으로 take를 교체하지 않는다. 완료 후보를 inbox에 넣고 그 작업을 만든 위치로 돌아갈 수 있게 한다.

## 이미지 편집: 한 샷 수정과 인물 기준 수정은 다른 작업

**선택 샷 수정**은 현재 그림·마스크·참조·편집 지시로 새 후보를 만든다. 브러시 mask, 원본/수정 비교, 인물·배경 보호 선택, 크롭/회전/색 조정, 생성 편집을 함께 제공한다. 간단한 크롭·위치·색 보정은 비파괴 composition 변경으로 충분하며 유료 재생성 없이 프리뷰한다. 생성 편집에서는 mask 밖 보존을 지시할 수 있으나 모델 보장을 가장하지 않는다. 실제 비교와 보호 영역 검사 후 선택한다.

**공통 인물 수정**은 기준 외형의 새 후보 판본을 만든다. 바로 전 샷의 그림을 모든 후속 샷에 덮는 기능이 아니다. ‘현재 샷만 / 현재 장면 / 이 상태를 쓰는 선택 샷 / 작품 기준 / 공유 기준 후보’로 적용 대상을 정하고 비용·사용처·비교 검토 대상을 보여준다.

이미지 수정 후 남겨야 할 연결은 `derivedFrom`, 편집 scope, 참조 판본, 실제 입력/출력 bytes, 선택한 mask, 이미지에서 인물이 위치한 영역이다. 결과 크기·구도가 달라지면 이전 focus point·camera safe bounds·말풍선 위치·레이어 마스크가 유효한지 다시 확인한다. ‘그림만 바뀌었으니 timing과 자막은 전부 유효’라는 가정은 성립하지 않는다.

새 얼굴이나 의상을 여러 샷에 이식할 때 영향 목록에서 예상 비용과 미완료 결과를 구별한다. 12개를 계획했지만 9개만 성공하면 채택된 9개와 미해결 3개를 보여준다. 실패가 이전 승인 파일을 지우지 않는다. 통일 적용 완료 전에도 과거 고정 출력판은 열 수 있어야 한다.

## 음성 생산: 배역 작업과 발화 연기를 분리한다

Casting Library에서 프로젝트의 모든 역할을 찾고 샘플을 청취해 음색을 채택한다. 오디션 문장·언어·발음·상태와 샘플 원음이 함께 남는다. Scene Inspector는 고정 음색에 이번 발화의 의도·말투·직전 응수 문맥을 더해 take를 생산한다. ‘이 인물 목소리 전체 변경’과 ‘이 문장만 다시 연기’가 서로 다른 범위다.

기본 출력은 편집 가능한 발화/의미 묶음 stem이다. 다화자 단일 파일은 adapter 제한·분리 가능성·정렬 검증을 표시한다. 하나의 자연스러운 대화 파일을 선택했을 때 화자 한 명만 교체할 수 있다고 약속하지 않는다. 긴 연속 발화에서 경계 분절이 품질을 낮추면 묶음 take를 유지하며 그 묶음 전체가 재생성 범위다.

다인물 테스트는 배역의 정체성 분리뿐 아니라 부재한 화자, 이름이 같은 두 인물, 회상 음색, 전화 effect, 내레이터와 내면 음성, 끼어드는 대화, 무발화 반응, 관객에게 정체를 숨기는 목소리를 포함해야 한다.

## local-first에서 클라우드로 옮길 수 있는 경계

첫 제품은 로컬 프로젝트·단일 durable worker·명시적으로 선택한 공급자 credential로 시작한다. 프로젝트를 열고 보존된 대본·이미지·음원을 편집하는 작업과 외부 생성 호출을 분리한다. 생성·검토·출력이 공급자 API나 원작 디렉터리의 생존에 모두 종속되어서는 안 된다.

초기부터 `ProjectStore`, `BlobStore`, `JobStore`, `WorkerRunner`, `CredentialResolver`, `SourceConnector`의 경계를 둔다. 구현은 로컬로 충분하다. UI가 절대 filesystem path나 API key를 제작 문서에 직렬화하지 않고 blob ID와 job ID로 접근한다. Connector만 원천 경로를 알고 export bundle은 닫힌 의존 집합과 자체 해시 검증을 갖는다.

클라우드 전환은 storage/queue backend를 바꾸는 것만으로 끝나지 않는다. 프로젝트 소유권·접근 제어·credential 격리·업로드 검증·서버 worker 권한·협업 충돌·삭제/보존 정책을 별도 출시 조건으로 둔다. 로컬 파일 접근 기능을 그대로 서버 임의 경로 접근 기능으로 복제하지 않는다. 긴 생성과 승인 race를 지금 판본 CAS로 막아두면 미래 팀 작업에서 같은 계약을 재사용할 수 있다.

프로젝트 portable bundle의 권고 내용은 schema manifest, 보존 원천, readable script/cast, 고정 에셋과 선택 음원, timeline, 검토 영수증, render 환경·출력 파일, 라이선스/권리 메모다. credential과 활성 provider handle은 제외한다. 목소리 provider ID가 만료되어도 이미 채택한 bytes의 편집·렌더는 가능해야 한다. 새 생성에는 재배역이 필요할 수 있음을 상태로 드러낸다.

## 제품 성공을 보여줄 대표 시연

같은 프로젝트에 40명 배역을 등록하고 한 장면에 여섯 명과 내레이터를 배치한다. 세 명은 대화하고 두 명은 듣고 한 명은 전화로 들린다. 회상 한 샷에서는 같은 인물의 어린 시절 음색·외형을 쓴다. 현재 장면에 필요한 트랙만 열고 멀리 있는 배역은 검색한다.

사용자가 한 샷의 손에 든 물건을 이미지 편집으로 수정한다. 원본과 후보를 비교하고 ‘이 샷에 사용’을 선택한다. 이어 중요한 인물의 기준 의상을 바꾸고 사용처와 예상 비용을 보며 두 샷에만 새 판본을 적용한다. 라이브러리 최신판과 이전 고정 샷이 공존한다.

마지막으로 대사 한 줄을 다시 연기시키고 침묵을 조정한다. 새 take 길이에 따라 timeline이 바뀌는 것을 실제 음원으로 듣고, 세로판 구도를 별도로 검토해 출력한다. 원작 연결과 provider credential을 끊은 환경에서 보존 bundle을 다시 열어 채택 파일로 렌더한다. 이 일련의 행위를 통과해야 ‘생산까지 가능한 독립 Studio’라는 주장을 할 수 있다. 첫 짧은 시연 길이가 제품의 최대 배역 수와 프로젝트 규모를 정하지 않는다.
