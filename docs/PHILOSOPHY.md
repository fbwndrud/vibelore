# vibelore의 방향과 철학

## 한 문장

vibelore는 소설을 대신 쓰는 규칙 모음이 아니라, **사용자가 원하는 독서 경험을 먼저 합의하고
AI의 창작 능력을 살리면서 장편에서 쉽게 무너지는 기억·인과·일관성·승인·복구를 책임지는
집필 기반**입니다.

## 우리가 만들려는 것

좋은 결과는 설정이 많거나 검사 점수가 높은 원고가 아닙니다. 독자가 어렵지 않게 상황을
이해하고, 인물의 선택을 납득하며, 다음 화를 읽고 싶고, 여러 화가 지나도 같은 작품처럼
느껴지는 원고입니다.

vibelore는 다음을 목표로 합니다.

1. **독서 계약을 먼저 정한다.** 장르명만 받지 않고 속도, 난도, 정서, 보상, 금기와 허용 범위를 StoryProfile로 합의합니다.
2. **깊이와 난도를 분리한다.** 깊은 주제도 쉽게 읽힐 수 있습니다. 기본은 쉬운 문장과 단계적인 개념 도입이며, 복잡성은 필요한 장면에서만 올립니다.
3. **인과가 장식을 이긴다.** 특별한 설정을 늘리기보다 행동, 반응, 결과가 서로 이어지게 합니다.
4. **인물을 설명이 아니라 누적으로 만든다.** 성격표를 반복하지 않고 선택, 대가, 관계 변화가 다음 화와 다음 아크에 남게 합니다.
5. **AI의 판단 공간을 남긴다.** 취향과 문체를 세부 금지 목록으로 고정하지 않습니다. 작품별 긍정 예시와 상위 약속을 주고 모델이 장면을 해결하게 합니다.
6. **사람이 마지막 권한을 가진다.** Markdown 원고가 정본이며, soft advisory는 자동 수정 명령이 아닙니다.
7. **실패해도 이어갈 수 있다.** 중단된 생성은 재개되고, 검사된 본문만 커밋되며, snapshot으로 복구할 수 있습니다.

## 책임의 경계

| 주체 | 책임 |
|---|---|
| 사용자 | 원하는 독서 경험, 중요한 취향, 최종 승인 |
| 호스트 AI | 아이디어 판단, 장면 구성, 대사와 산문 생성, 의미 비평 |
| vibelore MCP | 승인된 취향·정본·계획 전달, 순서 보장, 충돌 검사, 검토 근거·출처 기록, 상태 누적, 커밋과 복구 |
| Markdown 정본 | 세계, 인물, 본문과 요약의 최종 사실 |

결정론 코드가 문학적 취향을 판정하게 만들지 않고, AI가 정본 충돌이나 커밋 순서를 임의로
넘기게 두지도 않습니다. 잘하는 주체가 잘하는 일을 맡는 구조입니다.

## 설계 원칙

### 작은 Interface, 깊은 Module

사용자는 기본적으로 `lore_write`를 호출합니다. 내부에서는 계획, 컨텍스트 조립, 초고,
검사, 제한 수정, 영수증, 승인과 커밋이 이어집니다. 이처럼 작은 Interface 뒤에서 많은
복잡성을 처리하는 것을 **깊은 Module**이라고 부릅니다.

내부 단계를 전부 공개하면 호출 자유는 늘지만 잘못된 순서와 상태 분기가 사용자에게
전가됩니다. 그래서 기본 표면에는 웹툰 제작을 포함한 29개 완결형 도구만 보이고, 단계별 원시 도구는
`advanced` 표면에 둡니다.

### 상위 약속은 단단하게, 회차 선택은 얇게

```text
StoryProfile  독자가 어떤 경험을 할지
StorySpine    작품 전체가 어디로 움직일지
WriterSkill   그 경험을 어떤 산문으로 전달할지
ArcPlan       다음 몇 화에서 무엇이 변할지
EpisodePlan   이번 화의 압력과 전환이 무엇인지
Prose         실제 장면에서 인물이 어떻게 해결하는지
```

위로 갈수록 오래 유지되는 약속이고, 아래로 갈수록 모델의 현장 판단이 큽니다. 화별 계획이
문장과 농담까지 미리 쓰지 않으며, StoryProfile을 매 화 새로 해석하지 않습니다.

### hard와 soft를 섞지 않는다

- **hard invariant**: 확정된 사실 충돌, 검사 본문 hash 불일치, 잘못된 커밋 순서처럼 반드시 막아야 하는 문제입니다.
- **soft advisory**: 문체, 밀도, 감정 속도, 반복 가능성처럼 작가의 의도일 수도 있는 관찰입니다.

hard 위반은 고칩니다. soft 지적은 근거와 함께 보여주되 자동 재작성 이유로 쓰지 않습니다.
평균 점수 하나로 원고를 통과시키지 않고, 치명적인 개별 문제도 따로 봅니다.

높은 점수가 개별 지적을 지우지 않습니다. 검토가 실패한 상태도 좋은 평가와 구분해 기록하고,
원고를 보존한 채 사용자 판단으로 돌립니다. 조건부 자동 문체 재작성은 현재 도입하지 않았습니다.

### 예시는 작품에 속한다

장르 전체에 같은 금지 어투를 적용하지 않습니다. 캐릭터 말투 예시는 캐릭터에, 아크의
관계 변화 예시는 아크에, 작품 문체 기준은 승인된 StyleAnchor에 둡니다. 이 정보들은 서로의
역할을 침범하지 않습니다.

승인된 취향은 실제 집필 요청까지 도달해야 합니다. 선택한 문체 예시와 제외 이유를 기록하고,
사용자가 매 화 같은 선호를 되풀이하지 않아도 다음 집필에 전달합니다. 이것이 첫 원고의 재미를
보증하거나 이후의 취향 피드백을 불필요하게 만드는 것은 아닙니다.

### 평가의 근거와 한계를 함께 남긴다

동일 호스트의 자기검토를 독립 독자 평가라고 부르지 않습니다. 원고·계약 해시와 실제 요청·응답을
연결한 기록은 무엇을 평가했는지 확인하는 근거이며, 평가자가 성실히 읽었다는 증명은 아닙니다.
프로그램 검사 통과와 독자의 만족도 향상도 구분합니다.

## 하지 않는 것

- AI를 대체하는 자체 소설 생성 모델을 만들지 않습니다.
- 모든 장르를 하나의 문체나 난도로 통일하지 않습니다.
- 설정량, 전문 용어 수, 반전 수를 작품의 깊이로 간주하지 않습니다.
- 모든 취향 피드백을 영구 hard rule로 승격하지 않습니다.
- 캐릭터의 미래 서사를 처음부터 고정된 전기로 만들지 않습니다.
- 내부 평가용 실제 소설, 생성 원고와 일회성 실험 산출물을 제품 저장소에 보관하지 않습니다.
- 검증되지 않은 실험 기능을 기본 MCP 표면에 노출하지 않습니다.

## 새 기능을 넣는 기준

새 기능은 다음 질문을 통과해야 합니다.

1. 여러 장르와 작품에서 반복되는 문제인가?
2. 모델에게 더 좋은 맥락을 주는가, 아니면 선택을 과도하게 제한하는가?
3. 기존 Module 안에서 해결할 수 있는가?
4. 사용자가 알아야 할 새 도구가 정말 필요한가?
5. 실패했을 때 정본을 손상하지 않고 되돌릴 수 있는가?
6. 합성 fixture와 제품 테스트로 검증할 수 있는가?

특정 원고 한 편의 취향 문제라면 먼저 StoryProfile, WriterSkill, ArcPlan 또는 StyleAnchor에서
해결합니다. 여러 작품에서 같은 구조적 실패가 확인될 때만 엔진의 보편 규칙으로 올립니다.

## 성공 기준

vibelore의 성공은 기능 수가 아니라 다음 결과로 판단합니다.

- 처음 읽는 독자가 대화와 세계 정보에서 소외되지 않는다.
- 인물의 권한, 관계, 선택과 결과가 자연스럽게 이어진다.
- 작품이 요구한 읽기 난도와 정보 속도를 지킨다.
- 캐릭터의 과거 변화가 현재 행동에 남고, 다음 아크가 그 결과를 이어받는다.
- 여러 화를 생성해도 시점, 문체와 서술 밀도가 갑자기 바뀌지 않는다.
- 중단, 손수정과 재작성 뒤에도 정본과 내부 상태를 복구할 수 있다.
